# Canberra Traffic Forecasting

**An end-to-end machine learning system for forecasting road-level traffic congestion in Canberra, Australia.**

[**Explore the Live Dashboard**](https://shubhankaranagal.github.io/gb-electricity-imbalance-forecasting/) | [**View Source Code**](https://github.com/shubhankaranagal/gb-electricity-imbalance-forecasting)

Trained on approximately **26.7 million historical traffic observations**, this project forecasts congestion across **725 directed road segments**, 15, 30, 60 and 120 minutes into the future.

Four LightGBM models achieve **12–22% lower mean absolute error than a persistence baseline** on a held-out chronological test set.

The models are deployed through an automated live-data pipeline, with predictions presented on an interactive map showing expected delays and travel times.

## Results at a Glance

| Forecast horizon | Persistence MAE | LightGBM MAE | Improvement |
|---|---:|---:|---:|
| +15 minutes | 0.1684 | 0.1481 | 12.04% |
| +30 minutes | 0.1985 | 0.1670 | 15.85% |
| +60 minutes | 0.2242 | 0.1825 | 18.62% |
| +120 minutes | 0.2519 | 0.1960 | 22.17% |

All results are evaluated on an untouched chronological test set. MAE is measured in relative-delay units, where 0.10 corresponds to ten percentage points of free-flow travel time.

The persistence baseline assumes that congestion at the forecast horizon will equal currently observed congestion.

**Key finding:** The model's advantage over persistence increases with forecast horizon, from approximately 12% at 15 minutes to 22% at two hours.

## 1. Problem Formulation

### Why forecast relative delay?

Absolute travel time is heavily influenced by road-segment length. A two-minute journey may represent severe congestion on a short segment but free-flow conditions on a longer one.

To make congestion comparable across different roads, the primary forecasting target is **relative delay**:

\[
RD_{i,t}=\frac{TT_{i,t}-MinTT_{i,t}}{MinTT_{i,t}}
\]

where:

- \(TT_{i,t}\) is observed travel time for road segment \(i\) at time \(t\).
- \(MinTT_{i,t}\) is the segment's reference free-flow travel time.

For example, a relative delay of 0.50 indicates that the journey takes 50% longer than its free-flow reference.

Records with zero or invalid free-flow travel time are excluded from valid target calculations.

### Why not use the provider's unusual-delay metric?

Exploratory analysis showed that the supplied unusual-delay measure could produce counterintuitive temporal patterns, including elevated values during overnight periods.

Relative delay produced clearer weekday commuting peaks and offered a more directly interpretable measure of congestion.

This distinction matters: a statistically available target is not necessarily the best representation of the real-world problem.

### Forecasting objective

For each directed road segment, predict:

\[
\widehat{RD}_{i,t+h}
\]

for horizons \(h \in \{15,30,60,120\}\) minutes, using only information available at prediction time.

Predictions are also converted into absolute delay and expected segment travel time using the current free-flow reference.

## 2. Data and Preprocessing

### Historical data

The project uses historical traffic observations from the ACT AddInsight traffic system, covering approximately May 2020 to November 2023.

The historical dataset contains approximately **26.7 million observations**, including travel times, reference free-flow times, timestamps, road identifiers and network attributes.

### Data preparation challenges

**Temporal consistency**

Timestamps were standardised for chronological processing, while time-of-day features were constructed in Canberra local time.

Historical traffic lags were matched using actual elapsed time, rather than assuming that consecutive rows represented equally spaced observations.

**Road identity and geographical reconciliation**

Historical road identifiers and definitions were not completely stable.

Road geometry, site identifiers and directional relationships were investigated to establish consistent segment representations and connect the historical modelling data to the live network.

**Missing and invalid observations**

Undefined relative-delay targets, missing lag observations and unavailable live measurements were handled explicitly rather than silently replaced with artificial values.

## 3. Feature Engineering

The selected production model uses **25 features**, grouped into three categories.

### Temporal features

Cyclical representations of hour of day and day of week, together with a weekend indicator.

### Road and geographical features

Road length, lane count, freeway classification, projected origin and destination coordinates, segment midpoint, bearing and geography-resolution status.

### Recent traffic features

Current relative delay, historical relative delay at 5, 15, 30 and 60 minutes, and changes over recent 5-, 15- and 30-minute windows.

The live pipeline uses a 90-minute rolling observation history and matches lagged measurements within a ±150-second tolerance.

## 4. Modelling and Evaluation

### LightGBM forecasting

Four separate LightGBM regression models were trained, one for each forecasting horizon.

This allows each model to learn horizon-specific relationships between current conditions, recent traffic behaviour, road characteristics and future congestion.

### Chronological evaluation

Training, validation and testing follow chronological separation to avoid using future observations when predicting earlier traffic conditions.

Model selection was performed before evaluation on the held-out test period.

### Baseline comparison

The primary benchmark is persistence:

\[
\widehat{RD}_{i,t+h}=RD_{i,t}
\]

Persistence is a natural reference for short-term traffic forecasting, where current congestion often contains substantial predictive information.

The selected models outperform persistence at all four horizons.

### Network-feature experiments

Additional experiments investigated upstream and downstream traffic information derived from Canberra's directed road network.

These features introduced greater complexity without delivering a sufficiently convincing improvement over the selected model.

The simpler model was therefore retained for production.

This was a deliberate model-selection decision: additional features were not adopted merely because they represented a more sophisticated architecture.

## 5. Live Forecasting Architecture

The production system connects historical modelling work to an automated live application.

**Pipeline**

1. Retrieve current traffic observations from the ACT AddInsight API.
2. Load and update the persistent rolling traffic history.
3. Construct the same 25 features used by the trained models.
4. Run inference using four frozen LightGBM model files.
5. Convert relative-delay predictions into absolute delays and estimated travel times.
6. Publish the forecast dataset for the dashboard.

### Automated collection

GitHub Actions runs a burst collector designed to take five snapshots approximately five minutes apart.

Each successful snapshot updates the production files:

- `data/production/live_history.parquet`
- `data/production/live_forecasts.parquet`
- `docs/data/latest_forecasts.json`

### Separating application code and live data

The repository uses two branches:

- **`main`** — forecasting code, trained models, deployment configuration and dashboard.
- **`live-data`** — continually refreshed production history and forecasts.

The collector executes code from `main` while publishing generated snapshots to `live-data`.

This separation prevents routine data updates from continually changing the application's development branch.

### Forecast availability

The dashboard distinguishes between:

- **Full history:** the required recent lag observations are available.
- **Warming up:** some recent traffic history is missing.
- **Data unavailable:** the current measurement is invalid or missing.

Missing observations are not presented as reliable current measurements.

## 7. Running the Project

### Requirements

Python 3.12 and the following libraries:

```bash
pip install pandas numpy pyarrow requests lightgbm
```

### Run a single forecast update

From the repository root:

```bash
python src/live/update_forecasts.py
```

This fetches a current traffic snapshot, updates the local rolling history, runs the frozen models and writes the forecast outputs.

The first run may have incomplete lag history. Repeated collections allow the rolling history to accumulate.

### Preview the dashboard locally

```bash
python -m http.server 8000 --directory docs
```

Open `http://localhost:8000`.

The deployed dashboard reads published forecast data from the `live-data` branch. Local previewing therefore does not require running the scheduled GitHub Actions collector.

## 8. Limitations

**Baseline coverage:** Persistence is an important benchmark, but the reported results do not establish superiority over every possible historical, statistical or machine-learning forecasting method.

**Historical distribution shift:** Road conditions, travel patterns and network definitions can change over time. Historical test performance does not guarantee identical accuracy under current conditions.

**Live collection reliability:** GitHub Actions scheduling is best-effort. Delayed or missed runs can reduce the availability of recent traffic lags.

**Prediction uncertainty:** The dashboard presents point forecasts rather than calibrated prediction intervals.

**Segment-level predictions:** Forecasts describe individual directed road segments, not complete journeys or optimal routes.

**Operational monitoring:** A functioning automated pipeline is not equivalent to a fully monitored, high-availability production service.

## 9. Future Work

Potential extensions include:

- Stronger time-of-week and statistical forecasting baselines.
- Evaluation of live forecast errors as new ground-truth observations accumulate.
- Prediction intervals and uncertainty calibration.
- Drift monitoring and scheduled model retraining.
- Route-level travel-time forecasting.
